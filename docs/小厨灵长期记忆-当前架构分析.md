# 小厨灵长期记忆系统：当前架构分析

日期：2026-09-22

## 1. 分析范围

本分析基于当前 `main` 分支代码，重点检查了 Agent、AI 调用、用户身份、菜谱行为、Redis、数据库迁移、测试和可观测模块。

## 2. 技术基线

| 领域 | 当前实现 | 对长期记忆的结论 |
| --- | --- | --- |
| 后端 | Java 17、Spring Boot 3.3.6 | 继续使用，不引入新的应用框架 |
| ORM | MyBatis-Plus 3.5.7 | 记忆实体和 Mapper 沿用当前风格 |
| 数据库 | MySQL 生产、H2 测试、Flyway 迁移 | 长期事实和事件先落关系库，保证可审计 |
| 缓存 | Spring Data Redis | 适合 Session 工作状态、短期上下文和后续缓存 |
| AI | `QwenAgentClient`，兼容 OpenAI/Anthropic 风格请求 | 记忆抽取、重写和合并通过 Adapter 接入，不耦合 Controller |
| 认证 | JWT + `AuthPrincipal` | 所有记忆读写必须从认证主体取得 `userId` |
| 测试 | Spring Boot Test、Mockito、H2 持久化测试 | 每个记忆阶段同时补单元测试和迁移/隔离测试 |
| 前端 | Vue 3 + Vite 静态前端 | 当前阶段不改前端，先稳定后端领域模型 |

## 3. 现有模块与可复用能力

### 3.1 Agent

`com.example.food.agent` 已经具备：

- `agent_conversations` 和 `agent_messages`：持久化聊天会话和消息；
- `AgentService`：负责 SSE、模型多轮工具调用、对话写入和 Agent 恢复编排；
- `AgentToolRegistry`：统一工具定义和工具白名单；
- `AgentKitchenToolService`：把工具调用转成现有菜谱、冰箱、菜单、通知、反馈和用户资料服务调用；
- `AgentWriteService`、`AgentWriteOperationService`：确认、幂等和写操作结果留存；
- `AgentState`、`AgentRunStore`、`AgentEventStore`：基于 Redis 的短期运行状态、检查点和事件回放，默认 TTL 为 7 天；
- Agent 可观测快照和评测运行记录。

结论：长期记忆不能继续堆进 `AgentService`。应新增 `memory` 垂直子域，由 Agent 通过应用服务或工具桥接调用。

### 3.2 AI 与 Prompt

当前 `QwenAgentClient` 已提供统一的 Agent 模型调用，但系统提示和菜谱 Prompt 仍有一部分以内嵌字符串存在。数据库已有 `prompt_templates` 表，但目前没有统一的 PromptTemplateManager。

结论：第一阶段不改模型调用；后续抽取、Query Rewrite、Merge 和 Profile Consolidation 使用版本化 PromptTemplateManager，并保留模型、Prompt 版本和原始输出作为 provenance。

### 3.3 已有用户行为数据

现有表已经覆盖很多长期记忆的原始信号：

- `search_logs`、`search_log_ingredients`：搜索、输入类型、食材、餐次和目标；
- `recipe_records`、`recipe_ingredients`、`recipe_favorites`：生成菜谱、收藏和菜谱上下文；
- `recommendation_feedbacks`：喜欢/不喜欢反应和实际烹饪状态；
- `finished_dish_reviews`：上传成品图片后的 AI 评价记录；
- `pantry_operations`、`user_pantry_items`：库存、消耗和烹饪操作；
- `weekly_menu_plans`、`weekly_menu_items`：菜单选择和计划行为；
- `user_diet_preferences`、`user_health_profiles`、`user_health_nutrition_profiles`、`user_nutrition_targets`：用户明确填写的饮食和营养资料。

这些表是行为事实来源，不应直接改造成“记忆表”。长期记忆需要通过 Episode 保存统一来源和事件语义，再由后续抽取与合并流程生成。

### 3.4 数据隔离与一致性基础

当前业务服务普遍以 `userId` 作为查询条件，重要 Agent 写操作已有 `(user_id, idempotency_key)` 唯一约束、确认状态和重放机制。

结论：记忆表必须延续以下约束：

1. 所有用户可见查询显式带 `user_id`；
2. 事件写入使用 `eventId/idempotencyKey` 去重；
3. 领域更新保留 `version`，为后续乐观锁作准备；
4. 原始 Episode 不因合并而删除；
5. 删除长期记忆使用软删除或状态变更，保留审计能力。

## 4. 当前架构缺口

1. Agent 会话是聊天历史，缺少面向当前任务的 Session 工作上下文；
2. 现有行为事实分散在多个业务表，没有统一 Episode 和 provenance；
3. 没有 MemoryCandidate、Consolidated Memory、Structured Profile 的独立模型；
4. 没有个人 Memory RAG 与外部 Knowledge RAG 的边界和检索接口；
5. 没有版本化的记忆 Prompt 管理器；
6. 没有记忆级检索轨迹、抽取结果和评测指标；
7. `AgentService` 已经较大，继续加入记忆抽取或画像更新会扩大耦合和测试成本。

## 5. 第一阶段边界

第一阶段只建立可被后续阶段稳定依赖的持久化底座：

- 新增 Agent Memory Session 表和服务；
- 新增原始 Episode 表和幂等写入服务；
- 保存 session、事件来源、来源引用、事件载荷、发生时间、版本和删除状态；
- 用 MyBatis-Plus 和 Flyway 接入现有数据库；
- 补充用户隔离、幂等、并发版本和 H2 迁移测试。

第一阶段明确不做：LLM 抽取、标签归一化、Embedding、向量数据库、画像合并、Agent Tool 接入和前端页面。这些功能依赖底座稳定后逐阶段实现。
