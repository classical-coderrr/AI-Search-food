# 小厨灵长期记忆系统：架构与数据模型设计

日期：2026-09-22

## 1. 设计目标

长期记忆采用五层模型：

```text
Session → Episode → Structured Profile → RAG Memory → Personalized Skill
```

核心原则：

- Chat History 是会话展示和上下文来源，不等于长期记忆；
- Episode 保留行为事实和 provenance，Consolidated Memory 才表示可复用的长期判断；
- Structured Profile 是稳定、可快速读取的状态，不替代 Episode 或向量记忆；
- Memory RAG 与 Knowledge RAG 使用不同数据源、过滤器和评分链路；
- 用户显式表达优先于行为推断，任何推断都带 confidence 和 evidence；
- 新信息按 scope、时间、来源和置信度解决冲突，不直接覆盖旧事实。

## 2. 目标模块划分

```text
com.example.food.memory
├── api                 对外查询和记忆管理 DTO/Controller（后续阶段）
├── application         Session、Episode、Profile、Retrieval 应用服务
├── domain              记忆类型、来源、范围、衰减、冲突等规则
├── repository          MyBatis Mapper 与仓储接口
├── extraction          MemoryExtractor、Candidate、Prompt Adapter
├── normalization       CanonicalTag 与实体归一化
├── consolidation       Dedup、Merge、Confidence、Profile 更新
├── retrieval            Memory Query、Recall、Rerank、Context Builder
├── skill               Personalized Skill 生成和读取
├── infrastructure      Redis、LLM、Embedding、Vector Store Adapter
└── observability        记忆操作轨迹、指标和评测适配
```

第一阶段只实现 `application`、`domain`、`repository` 的 Session/Episode 子集，避免修改现有 Agent 主编排器。

## 3. 运行时数据流

```text
用户对话/业务行为
        │
        ├─ 当前请求 → Agent Session（Redis 工作状态 + MySQL 元数据）
        │
        └─ 事实事件 → Episode（原始、可审计、幂等）
                           │
                           ▼
                 Memory Extraction（后续）
                           │
                           ▼
             Candidate → Normalize → Dedup/Merge
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
      Structured Profile          Memory Index
             │                           │
             └──────────┬────────────────┘
                        ▼
       Query Planner → Memory RAG → Rerank → Context Budget
                        │
                        ▼
              Personalized Skill + Agent Reasoning
                        │
                        ▼
                  用户反馈 → 新 Episode
```

Session 是当前任务的工作记忆，Episode 是跨会话可追踪的事件记忆。Session 过期不等于 Episode 删除。

## 4. 关键服务边界

| 服务 | 职责 | 不负责 |
| --- | --- | --- |
| `MemorySessionService` | 创建、续期、关闭和读取当前任务 Session | LLM 抽取、长期偏好合并 |
| `MemoryEpisodeService` | 以幂等方式保存和查询原始 Episode | 判断用户是否真正喜欢某事 |
| `MemoryExtractor` | 从 Session、对话和行为生成候选记忆 | 直接写最终 Profile |
| `TagNormalizationService` | 将别名映射到 canonical tag | 处理偏好强弱 |
| `MemoryDedupService` | 找出语义和规范实体相似的候选 | 删除原始 Episode |
| `MemoryMergeService` | 合并证据、计算 confidence 和权重 | 直接修改用户输入原文 |
| `MemoryConflictResolver` | 处理长期偏好和近期状态冲突 | 无视当前任务上下文 |
| `ProfileConsolidationService` | 从有效 Memory 更新结构化画像 | 存储完整历史事件 |
| `MemoryRetriever` | 用户隔离后的召回和多因子排序 | 检索外部知识 |
| `KnowledgeRetriever` | 菜谱、营养资料和用户上传知识检索 | 读取个人 Memory |
| `ContextBuilder` | 按任务和预算组装 Profile、Memory、Knowledge 和工具结果 | 承担 Agent 工具执行 |
| `PersonalizedSkillService` | 将稳定行为模式转为任务策略 | 把一次行为当成长期技能 |

## 5. 长期数据模型

### 5.1 已在第一阶段实现

#### `agent_sessions`

面向当前 Agent 任务的工作上下文，与 `agent_conversations` 解耦但可关联。

| 字段 | 说明 |
| --- | --- |
| `id` | Session ID |
| `user_id` | 强制用户隔离 |
| `conversation_id` | 可选关联现有 Agent 会话 |
| `session_key` | 客户端或 Agent 侧幂等键，按用户唯一 |
| `status` | ACTIVE、COMPLETED、EXPIRED、CANCELLED |
| `current_task/current_goal` | 当前任务和目标的轻量结构化字段 |
| `context_json` | 当前约束、实体和临时偏好；不当作长期画像 |
| `selected_memory_ids_json` | 本次选择的记忆 ID 快照 |
| `retrieved_knowledge_ids_json` | 本次知识检索 ID 快照 |
| `agent_state_json` | Agent 工作状态摘要，不替代 Redis checkpoint |
| `started_at/last_activity_at/expires_at/ended_at` | 生命周期 |
| `version` | 更新时的乐观锁版本 |
| `deleted_at/created_at/updated_at` | 软删除和审计时间 |

Redis 后续以 `memory:session:{userId}:{sessionId}` 缓存完整工作状态，MySQL 保留可追踪元数据。

#### `memory_episodes`

保存事实事件，不保存“用户一定喜欢某物”的最终判断。

| 字段 | 说明 |
| --- | --- |
| `id` | Episode ID |
| `user_id/session_id/conversation_id` | 用户和来源会话 |
| `episode_type` | RECIPE_EXPERIENCE、SEARCH、PANTRY_CHANGE、PREFERENCE_DECLARATION 等 |
| `source_type` | CHAT、RECIPE_SAVE、RECIPE_FEEDBACK、COOKING、PANTRY、PROFILE 等 |
| `source_id` | 业务表或消息表的来源 ID |
| `event_id/idempotency_key` | 重试和重复事件去重 |
| `summary` | 可读摘要 |
| `payload_json` | 原始事件上下文，保留 recipe、scene、action 等字段 |
| `occurred_at` | 行为真实发生时间 |
| `status` | RAW、PROCESSING、PROCESSED、REJECTED |
| `importance` | 后续抽取和检索的初始重要性 |
| `deleted_at/version/created_at/updated_at` | 生命周期、并发和审计 |

第一阶段不删除 Episode，后续合并只改变处理状态或软删除状态。

### 5.2 后续阶段表

#### `memory_candidates`

保存抽取模型的中间结果：`memory_type`、`entity`、`canonical_tag_id`、`polarity`、`strength`、`confidence`、`source_type`、`evidence_json`、`model_name`、`prompt_version`、`status`。候选可以被拒绝，但原始 Episode 不受影响。

#### `memory_evidence`

保存候选或 Consolidated Memory 的证据引用：`memory_id`、`episode_id`、`source_message_id`、`evidence_type`、`evidence_text`、`explicitness`、`user_confirmed`、`created_at`。它是 provenance 的可查询形式，不用一个大 JSON 隐藏所有来源。

#### `memory_items`

保存去重合并后的长期事实：`user_id`、`memory_type`、`canonical_tag_id`、`entity_key`、`polarity`、`scope`、`temporal_type`、`valid_from/valid_to`、`base_weight`、`confidence`、`importance`、`evidence_count`、`occurrence_count`、`first_seen_at/last_seen_at`、`status`、`version`。

#### `user_profiles`

按用户一行保存结构化画像的稳定快照和版本：口味数值、烹饪时长统计、难度偏好、当前饮食目标摘要等。高频查询字段关系化；低频、可演化字段使用受控 JSON；不把 Episode 原文塞进 Profile。

#### `memory_preferences`

保存用户级可编辑偏好视图，与已有的 `user_diet_preferences` 区分：后者是用户填写的当前设置，前者是带证据、置信度、来源和时间范围的演化事实。

#### `canonical_tags`

保存 `canonical_name`、`category`、别名、启用状态和可选 embedding。归一化先用规则/别名，后续再接 Embedding，避免把简单同义词问题交给模型。

#### `memory_embeddings`

保存 `memory_id`、`user_id`、`memory_type`、向量、metadata、模型版本和更新时间。所有向量查询强制包含 `user_id`；Memory RAG 和 Knowledge RAG 不共用集合。

#### `personalized_skills`

保存 `skill_key`、策略 JSON、来源 Memory ID、confidence、版本和有效期。一次短期行为只能影响候选策略，不能直接生成稳定 Skill。

#### `memory_conflicts` / `memory_feedback`

分别保存冲突双方、解析结果、当前任务和用户确认，以及用户对记忆的 CONFIRM、REJECT、ONLY_THIS_TIME、DELETE 等反馈。

#### `memory_retrieval_traces`

保存 traceId、query、候选 ID、过滤条件、检索分数、重排分数、最终使用 ID、模型和延迟，为“为什么推荐这道菜”提供解释链。

## 6. 衰减、置信度与冲突

最终有效权重采用配置化策略：

```text
effectiveWeight = baseWeight × confidence × importance × decay(temporalType, age)
```

至少配置以下衰减类型：

- `EXPLICIT_PREFERENCE`：慢衰减，用户明确修改前保持高优先级；
- `IMPLICIT_PREFERENCE`：中等衰减，需要多次证据增强；
- `SHORT_TERM_TREND`：快速衰减，表达“最近”；
- `BEHAVIOR_PATTERN`：按重复行为和近期性计算；
- `TEMPORARY_CONTEXT`：只在 Session 或有效期内生效。

冲突解析顺序：用户明确确认 > 当前任务 scope > temporalType > confidence > evidenceCount > 新旧时间。这样“长期喜欢辣”和“最近想吃清淡”可以同时保留。

## 7. Memory RAG 与 Knowledge RAG

两套 Retriever 使用不同接口和数据源：

```text
MemoryQueryPlanner → MemoryRetriever → MemoryReranker
KnowledgeQueryPlanner → KnowledgeRetriever → KnowledgeReranker
```

Memory 检索必须带 `userId`、记忆类型、场景、餐次、时间范围、置信度和重要性过滤；排序由 `MemoryRankingConfig` 配置语义相似度、近期性、重要性、置信度、反馈和上下文匹配权重，不能把固定 TopK 当作业务逻辑。

## 8. MCP 边界

当前不直接增加 MCP Server。所有记忆能力先通过稳定的 Application Service 暴露：

```text
searchMemory
getUserProfile
saveEpisode
updatePreference
getPersonalizedSkill
recordRecipeFeedback
searchUserRecipeHistory
```

后续 MCP 只做薄适配层，映射到同一套 Service，避免出现两套权限、幂等和用户隔离逻辑。
